# Фоновые отчёты WB: дизайн

## Цель

RNP, реклама, P&L и остатки никогда не выполняют тяжёлый расчёт в HTTP-запросе. Клиент получает готовый кэш либо состояние фоновой задачи и не показывает статические моковые строки.

## Границы

- Используем уже существующий `source_cache` и отдельный ads cache; новую таблицу БД не создаём.
- Ключ задачи: организация, идентификатор отчёта, период и группировка.
- Один ключ может иметь одну активную задачу. Повторный запрос возвращает её статус.
- Если по точному ключу есть прошлый результат, ответ содержит его вместе со статусом `queued`/`running` и признаком устаревших данных.
- Клиент запускает обновление только через endpoint фоновой задачи и опрашивает её статус. Обычный GET читает кэш и никогда не запускает тяжёлый расчёт.

## API

Для каждого из `rnp`, `ads`, `pnl`, `stock` добавляются совместимые поля `reportJob` и `stale` в GET-ответ, а также два универсальных маршрута:

- `POST /api/wb/reports/{report_id}/jobs` — создаёт задачу или возвращает уже активную для переданного периода;
- `GET /api/wb/reports/{report_id}/jobs` — возвращает состояние задачи по периоду.

Состояния: `idle`, `queued`, `running`, `completed`, `failed`. Ответ задачи включает понятный этап, процент и текст ошибки без раскрытия внутреннего traceback.

## Исполнение

Celery-задача использует существующие функции построения отчётов. Она сохраняет результат в тот же точный cache key, который читает GET. Это исключает параллельный повторный расчёт и сохраняет данные между рестартами API.

## Фронтенд

React-островки RNP, Ads, P&L и Stock всегда заменяют весь статический `#tab-*` контейнер. Их таблицы имеют только три честных состояния: загрузка, данные, ошибка. При `stale` показывается последний готовый результат и индикатор обновления; при `failed` — сообщение и кнопка повторного запуска.

Legacy `renderSecondaryReports` остаётся изолированным от этих четырёх контейнеров и не может записывать в их DOM.

## Проверки

- backend unit tests: dedup задач, чтение stale-кэша, ошибка задачи, GET без запуска расчёта;
- frontend source/component tests: отсутствие статических строк и вызов job endpoint/polling;
- typecheck фронтенда и точечные pytest.
