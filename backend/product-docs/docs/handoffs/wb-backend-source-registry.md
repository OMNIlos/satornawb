Дата: 2026-05-25
Статус: Sprint A working register.
Scope: WB first / INDEEPA replacement.

## 1. Правила registry

Каждая production-метрика или risky action должна иметь строку в registry. Если source, formula, fallback или freshness неизвестны, строка остается в статусе `blocked`/`unknown`, а API возвращает typed state с blocker ID.

Допустимые статусы:

- `confirmed` - source/formula/fallback/freshness подтверждены;
- `needs_api_discovery` - нужен WB endpoint/export/field proof;
- `needs_client` - нужно решение Марии/Максима;
- `manual_fallback` - production допустим через ручной ввод/Excel;
- `requires_own_cache` - внешний API дает только текущий срез, production-история возможна только через свой snapshot cache;
- `business_config` - источник не WB, нужна настройка/порог продукта;
- `blocked` - нельзя считать production-ready;
- `disabled` - intentionally out/P2.

## 3. Backend implementation notes

- Store registry rows in a table or seed file that can be promoted into a table in Sprint A.
- Keep blocker IDs as first-class array fields, not prose-only notes.
- Do not mark a row `confirmed` unless source, formula, fallback and freshness rules are all filled.
- `confirmed` for frontend contract shape is not the same as confirmed production data source.
- Critical price rows must block `price apply`, not just show warnings.
