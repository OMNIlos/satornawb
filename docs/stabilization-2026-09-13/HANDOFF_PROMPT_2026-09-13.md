# Промпт для продолжения разработки Satorna: шесть направлений

Ты продолжаешь существующий проект Satorna — CRM для бизнеса на Wildberries. Работай как профессиональный AI Engineer / Data Scientist: минималистичный качественный код, проверяемые расчёты, понятный UX и измеримая производительность.

Моя задача для тебя — выполнить доступную работу по шести направлениям ниже, а не ограничиться новым общим аудитом или планом. Начни с актуализации состояния, выбери небольшой проверяемый пакет и переходи к реализации. Если одна задача зависит от недостающего ответа, продолжай остальные. Не обещай скрытую работу после окончания ответа.

Этот промпт создан по моему новому прямому запросу. Старые записи в документах «не создавать промпт нового чата до получения эталона» больше не ограничивают передачу работы. Сам эталонный финансовый файл при этом всё ещё ожидается: его отсутствие нельзя считать разрешением придумать финансовые правила.

## 1. Цель и границы проекта

Нужен работающий текущий WB-контур CRM:

- Метрики имеют подтверждённый источник, период и понятное определение; неизвестные значения не подменяются нулями.
- Готовые данные открываются быстро; новый ещё не полученный от WB период имеет честный статус фоновой загрузки.
- Основные desktop/mobile-сценарии не содержат известных блокирующих UX-дефектов.
- Каждая правка проверена, выпуск воспроизводим, откат сохранён.

Не начинай переписывать всю архитектуру. Переиспользуй существующие компоненты, кэш, фоновые задания, тесты и release gate. Не добавляй зависимости, второй планировщик или новый мониторинговый стек без доказанной необходимости.

Новые разделы Avito, полноценная интеграция 1С и достройка всех ComingSoon не входят в этот пакет WB-готовности. При изменении общих функций сохраняй работающие сценарии Avito. Не обещай «ноль багов навсегда» или срок четыре дня из старого исходного промпта.

## 7. Проверка, выпуск и отчёт

Для каждого пакета: воспроизведение → минимальное исправление → проверка → scoped review → отдельный коммит только своих готовых файлов. Новый тест должен действительно проверять наблюдаемое поведение; collection error не считать RED. Не смешивай старые результаты с новым прогоном.

Проверяй UI на одинаковых данных и размерах до/после: desktop 1366/1440/1920px, mobile 390px, масштаб 200%, клавиатура и состояния ошибок. По одному скриншоту не объявляй весь UX или доступность принятыми.

Готовые frontend-пакеты можно выпускать по ранее согласованному процессу: замороженный проверенный источник → отдельный stage без переключения домена → проверка → promotion того же deployment → live QA → сохранённый откат. Перед переключением проверь, что production не был изменён другим исполнителем. Backend production не выкатывать при прежнем дефиците диска и без закрытия условий обслуживания.

Vercel в двух предыдущих выпусках менял только порядок JS modulepreload. Историческое разрешение касается исключительно конкретных старых пар хэшей. Новое отличие нельзя автоматически игнорировать или объявлять byte-exact: исследуй отдельно либо обеспечь выпуск именно проверенного артефакта.

Не используй боевые импорт, экспорт с побочным созданием задачи, одобрение цен и другие записи как read-only smoke-test. После собственной QA корректно выйди, проверь отзыв своей сессии и закрой только свой браузер.

Обновляй статусы задач исходного backlog по их ID, приёмку, фактические замеры и отчёт. В итоговом сообщении раздели:

1. Что реализовано и чем проверено.
2. Что опубликовано: commit/deployment и результат live QA.
3. Что готово только локально либо остаётся непроверенным.
4. Какие метрики действительно сверены, а какие ждут источника/эталона.
5. Какие конкретные ответы или доступы ещё нужны от меня.

Не переоценивай готовность: «66%» — индикатор этапов данных, не готовность проекта; 183 мс ранее были одним готовым P&L-запросом, а 5 мин 42 с — подготовкой другого нового диапазона. Новые обещания скорости делай только по собственным сопоставимым измерениям.

Начни с чтения контекста, проверки текущего состояния и краткого сообщения, какой первый пакет берёшь. Затем выполняй доступные подтверждённые задачи, а не возвращай ещё один общий список рекомендаций.
