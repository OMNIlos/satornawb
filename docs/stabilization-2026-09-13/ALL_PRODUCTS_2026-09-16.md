## Продолжение 17 сентября: приоритет над историческими ограничениями ниже

Владелец уточнил: база маржи — окончательная выплата после удержаний WB;
ABC — продажи в штуках / прибыль; внутренние расходы компании пока исключены.
Отсутствие внутренних расходов больше не является блокировкой этой версии.

Локально добавлен versioned settlement-контракт `wb-final-payout-cogs-tax-v1`.
Сохранены прежняя выручка и старые поля API для совместимости других consumers.
Новая выплата: payable − logistics − storage − acceptance − penalty − deduction
− loyalty − Finance promotion + signed additionalPayment. Комиссия и эквайринг
уже внутри payable и повторно не вычитаются. Ads fullstats не прибавляется к
Finance promotion. Прибыль: выплата − датированная себестоимость нетто-продаж
− существующий подтверждённый налог. Новые денежные политики не записываются.
Это локальная реконструкция по существующей нормализации Finance, ещё НЕ
независимая сверка окончательной выплаты с контрольным файлом владельца.

границы 80/95%, пересекающий порог SKU остаётся в предыдущем классе,
равенства разрешаются стабильным идентификатором. Нулевые/отрицательные

полный финансовый набор аккаунта/периода, включая отсутствующие в каталоге SKU.
Поиск и страницы не пересчитывают класс. Неизвестный член блокирует свою ось.
Несверенные/нераспределённые расходы аккаунта блокируют прибыльный класс.
Пограничные соглашения алгоритма зафиксированы явно; реальная финансовая

## Найденная цепочка и ограничения

- `app/repricer_bff.py` собирает сохранённые товары, цены, воронку и периодические
  события. `app/routers/wb_repricer_bff.py` накладывает Finance и налог,
  строит summary до пагинации. `liveParityData.ts` переносит DTO в runtime;
  `VellaHtmlParityPage.tsx` и HTML snapshot отрисовывают страницу.
- Выручка: существующий `revenueKopecks`/Finance retailAmount с возвратами.
  В этом пакете арифметика, источники и фильтрация выручки не изменяются.
- `payableKopecks` из `forPay`/`ppvz_for_pay` — отдельное поле Finance.
  Равенство окончательной выплате после всех удержаний не доказано.
  Новая формула маржи заблокирована только выбором этой базы, не всей задачей.
  Старый результат repricer не является окончательной чистой прибылью.
- Отчёт 15 сентября фиксирует продажи за вычетом возвратов и 750 bps с
  01.09.2026 по Москве. Повторно спрашивать ставку/эти записанные правила не нужно;
  это не разрешение перезаписать политики других аккаунтов.
- `ordersUnits`: приоритет `funnelOrderCount`, иначе периодические заказы.
  В fallback отмены исключаются и считаются отдельно; единицы дедуплицируются
  по имеющемуся ключу. Продажи/возвраты — другая когорта. В старом ingestion сумма
  finishedPrice временно считается для средней, затем удаляется. Summary не
  предоставляет согласованную денежную сумму заказов. Нельзя восстановить её
  умножением округлённой средней либо текущей цены на количество из воронки.
- `inSale`: backend и клиентский fallback проверяют stock > 0 и исключают
  liquidation, но не проверяют действующую цену. Нет доказательства совпадения
  размерного остатка и цены одного варианта. Требуется отдельное исправление
  проекции с данными о вариантах/свежести; старый счётчик не принят по новому ТЗ.

## ABC

`_apply_abc_codes` сортирует по salesUnits, затем ordersUnits/revenue; классы
назначает по доле числа строк (20/50%), не накопленному вкладу. Второй ранг
использует `netProfitKopecks or 0`; это допускает буквы при неизвестной прибыли.
`netProfitKopecks` legacy repricer не доказывает учёт внутренних расходов.

Локальный consumer больше не подставляет CC и не показывает второй legacy-ранг
как подтверждённый прибыльный ABC. При старом корректном коде остаётся A—/B—/C—,
с объяснением legacy-методики; при отсутствии кода — неизвестно. Backend и
методика классификации пока не изменены. Это защитная совместимость, не готовая
новая классификация. Новые пороги/метрика/правило пересечения требуют решения.

## Комментарии

На этой странице `addReportComment`/`addDrawerComment` пишут в REPORT_COMMENTS
в браузере, с демонстрационными автором и временем. Отрисовка текста использует
escapeHtml. Это НЕ совместное хранилище. В legacy backend найден SKU_COMMENTS
в памяти; hydration/flush runtime не сохраняет его. Подключение постоянных
комментариев с organization/account/product scope, автором из сессии, аудитом,
версией и конфликтом 409 требует отдельного согласованного persistence-этапа.
Нельзя просто подключить существующий глобальный словарь и назвать это parity.

## Стратегии

Цепочка кода существует: `applyLiveRepricerStrategy` → bulk assignment route →
`apply_frontend_strategy_assignment` → hydrate/flush organization runtime →
`_resolve_strategy_id` в `repricer_execution.py` → исполнитель/защитные проверки.
Корзины выбирают baskets_orders_4599, динамика — revenue_dynamics_4600.
Это не только подпись. Но факт кода не заменяет нового сквозного fake-прогона.
Bulk UI явно передаёт executeAfterAssign=true, одиночное назначение — false;
назначение и запуск расчёта поэтому нужно объяснять раздельно. Scheduler читает
workerAutoApplyPricesEnabled; применять цены в проверке нельзя. Существующий
`test_execute_with_worker_approval_creates_pending_without_applying` проверяет
approval boundary, но в этом пакете ещё не запускался. Изоляция runtime по
аккаунтам/конкурентным запросам требует отдельной проверки, не считается доказанной.
